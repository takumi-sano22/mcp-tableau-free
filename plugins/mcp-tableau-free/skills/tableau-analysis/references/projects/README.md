# プロジェクト固有の reference の書き方

このディレクトリには、**そのプロジェクトでしか通用しない内容**だけを置く。
汎用の作法は上位の reference（`data-handoff.md` / `workbook-generation.md` /
`analysis-recipes.md` / `official-sources.md`）に置き、ここでは重複させない。

プロジェクトごとにディレクトリを切る（名前は kebab-case）。

```
references/projects/
├── README.md              ← このファイル（書き方のテンプレート）
└── <project>/
    ├── README.md          プロジェクト固有のドキュメント
    └── *.py               そのプロジェクト専用のスクリプト
```

**スクリプトも同じディレクトリに置く。** 手順だけ書いて次回また書き直すより、動いたものを
残すほうが速い。汎用化できる部分が見えたら上位の `scripts/` へ引き上げる。

## 置く内容

| 節 | 書くこと |
| --- | --- |
| 対象データ | どこにある何を可視化するのか。ディレクトリと形式 |
| データの癖 | 系列ごとのスキーマ差・比較できない区切り・除外条件など、知らないと誤読するもの |
| テーブル設計 | 実際に作ったテーブルと列の意味。特に集計方法を間違えやすい列 |
| 再現手順 | 抽出 → Hyper 生成 → ワークブック生成のコマンド |
| 環境 | ファイルの置き場所（作業用と Tableau に渡す用）、雛形の場所 |
| 確認済みの数値 | 一次情報と突き合わせた結果。次回の回帰確認に使う |

## 置かない内容

- Tableau 一般の作法（上位 reference に書く）
- そのとき限りの試行錯誤の記録（作業ログに書く）
- 認証情報・個人を識別できる値

## 書き方

- **なぜそうするかを添える。** 「この列は SUM で扱う」だけでなく「件数なので平均は誤り」まで書く
- 数値は出どころのファイルパスとセットで書く。後から検証できるようにする
- 実測していないことは「未確認」と明記する
